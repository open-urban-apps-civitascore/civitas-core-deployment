# Apache NiFi

Dataflow orchestration cluster (Apache NiFi 2.x) deployed via Helm chart.

This component deploys NiFi as a StatefulSet using a Helm chart, hosted in
the [`apache-nifi-helm`](https://gitlab.com/civitas-connect/civitas-core/civitas-core-v2/apache-nifi-helm)
GitLab package registry. The chart uses **Kubernetes-native state management** (Leases for
leader election of Cluster Coordinator and Primary Node, ConfigMaps for processor state)
so no ZooKeeper is required.

## Why Helm chart (not an Operator)

- Lower complexity: no controller, no CRDs — an operator is oversized for a single cluster.
- Transparency: Helm values + chart are the single source of truth.
- Independence: a Helm chart is more easily interchangeable than an operator.
- Direct troubleshooting via standard Kubernetes resources.

## Required (external) components

- **Keycloak** — OIDC identity provider. Two clients live in
  `components/nifi/keycloak-clients.yaml`:
  - `nifi` — confidential, Authorization Code flow, used by the browser UI / REST API.
    Its client secret is auto-generated by the `secrets` component as
    `keycloak-client-nifi`.
  - `nifi-direct` — public, **Resource Owner Password Credentials** (Direct Access
    Grants) flow, used by in-cluster machine identities (`nifi-bootstrap` Job and
    `config-adapter`). No client secret required.

  Two dedicated realm users (in the same realm config) back the DAG flow:
  - `nifi-admin@internal.local` — NiFi's "Initial Admin Identity", used by the
    bootstrap Job.
  - `nifi-config-adapter@internal.local` — used by the config-adapter component.

  Their generated passwords are stored as Kubernetes Secrets
  `nifi-admin-keycloak-user` and `nifi-config-adapter-keycloak-user` by the `secrets`
  component (declared in `components/nifi/secrets.yaml`).
- **cert-manager** (optional) — used by the chart for inter-node TLS certificates.
- **Prometheus** (optional) — scrapes `ServiceMonitor` and `nifiMonitor` when
  `global.metrics.enabled = true`.

### In-cluster REST API client

The `config-adapter` component is the **only** in-cluster client allowed to call the NiFi
REST API (enforced via `NetworkPolicy`). It authenticates via OIDC using the public
`nifi-direct` Keycloak client with the **Resource Owner Password Credentials** (Direct
Access Grants) flow, posting `nifi-config-adapter@internal.local`'s password to
`/realms/<realm>/protocol/openid-connect/token` and sending the resulting Keycloak
access token to NiFi as `Authorization: Bearer <token>`.

NiFi resolves the calling identity from the JWT's `preferred_username` claim (set via
the OIDC property `claim_identifying_user = preferred_username`), which for a realm
user equals the username — i.e. `nifi-config-adapter@internal.local`. That identity is
provisioned as a NiFi user with the required REST policies by the `nifi.bootstrap`
post-install Job (see [Initial admin and bootstrap](#initial-admin-and-bootstrap)).

## Initial admin and bootstrap

NiFi 2.x's `FileAccessPolicyProvider` grants the "Initial Admin Identity" only a
**minimal global** policy set on first boot (flow R, controller R/W, policies R/W,
tenants R/W, restricted-components W). It does **not** create root-process-group R/W,
parameter-contexts, provenance, counters, system or site-to-site policies — so an
operator who tries to use the UI immediately gets *"No applicable policies could be
found"*.

This component solves that automatically:

1. **`initial_admin_identity` is a dedicated realm user**, not a human and not a
   Keycloak service account. The chart sets it to `nifi-admin@internal.local`, a
   realm-managed user declared in `components/keycloak/values/config/base-values.yaml.gotmpl`
   whose password is generated by the `secrets` component and stored in the Secret
   `nifi-admin-keycloak-user`. On first boot NiFi grants *that* user the global admin
   policies.
2. **The `nifi.bootstrap` part** is a Helm post-install / post-upgrade Job (chart
   `components/nifi/charts/nifi-bootstrap`) that:
   - Obtains an access token for `nifi-admin@internal.local` from Keycloak via the
     **Resource Owner Password Credentials** grant against the `nifi-direct` public
     client.
   - Waits for the NiFi REST API to come up.
   - Idempotently creates two NiFi users and the full policy set each one needs:
     - `global.initialUserEmail` (the human admin) — full operator policies including
       root-PG R/W, parameter-contexts, provenance, counters, system, site-to-site, …
     - `nifi-config-adapter@internal.local` (the in-cluster REST client) — flow R,
       controller R, root-PG R/W, parameter-contexts R/W, restricted-components R/W,
       proxy R/W.
3. Re-running `helmfile apply` is safe: every step is `GET → create-if-missing` or
   `PUT-merge`, so the Job converges to the desired policy set.

> **Why DAG / password grant for the bootstrap, not client_credentials?**
>
> NiFi 2.x's bearer-token resolver reads the JWT's `sub` claim, which for a Keycloak
> service account is an opaque UUID. The OIDC property `claim_identifying_user`
> is only honoured on the browser code-flow paths (`/access/oidc/callback`), not on
> the resource-server bearer-token path. With a real realm user, the JWT's
> `preferred_username` matches a stable username we can register as the Initial Admin
> Identity. There is no `/access/oidc/exchange` endpoint in NiFi 2.x, so we cannot
> coerce the identity client-side. Alternatives that were considered and ruled out
> include the single-user provider, LDAP, and mTLS via cert-manager.
>
> The Resource Owner Password Credentials grant is **deprecated by OAuth 2.1** but
> remains an acceptable trade-off in the internal CIVITAS setting — the password is
> never exposed outside the cluster (mounted as a file inside the Job pod, not as
> an env var) and is rotated by regenerating the Kubernetes Secret.
>
> **Tech debt:** the password grant is a deliberate stop-gap. Revisit once NiFi
> exposes a bearer-token identity-mapping hook (or an OIDC token-exchange endpoint)
> that lets a Keycloak service account (`client_credentials`) be resolved to a
> stable NiFi identity — at which point this realm user + DAG flow can be dropped.


## Other requirements

- StorageClass capable of provisioning the configured PersistentVolumeClaims
  (`config`, `state`, `logs`, `flowfile`, `content`, `provenance`).
- NiFi 2.0+ for Kubernetes-native state management.

## Configuration

Default environment values (see `default-environment.yaml.gotmpl`):

| Key                                  | Default                                         | Description                                                       |
|--------------------------------------|-------------------------------------------------|-------------------------------------------------------------------|
| `nifi.nifi.enabled`                  | `true`                                          | Toggle deployment of the NiFi release                             |
| `nifi.nifi.namespace`                | derived via `civitas.namespace`                 | Target namespace                                                  |
| `nifi.nifi.nodeCount`                | `1`                                             | Number of NiFi nodes (single-instance deployment in all profiles) |
| `nifi.nifi.initialAdminEmail`        | `global.initialUserEmail`                       | Human operator the bootstrap Job grants full NiFi admin to (not NiFi's Initial Admin Identity) |
| `nifi.nifi.bootstrapAdminIdentity`   | `nifi-admin@internal.local`                     | NiFi's `initial_admin_identity`; the technical user the bootstrap Job authenticates as. MUST equal `bootstrap.oidc.adminUsername` |


Environment profiles:

- **base** (`values/nifi/base-values.yaml.gotmpl`) — OIDC via Keycloak, Kubernetes state
  management, ZooKeeper disabled, chart ingress disabled, internal-only `ClusterIP`
  service (no APISIX route), metrics gated by `global.metrics.enabled`. Deployed as a
  single instance (`nodeCount: 1`).
- **development** — 1 node, 1Gi/2Gi resources, 512m/1g JVM heap, small PVCs, PDB off.
- **production** — 1 node, 2/8Gi → 4/12Gi resources, 4g/6g JVM heap, large PVCs
  (`flowfile 20Gi / content 50Gi / provenance 100Gi`), PDB disabled (single instance),
  `nifiMonitor` x1.

## Access

NiFi is deployed **internal-only** — it is not reachable from the internet and there is no
APISIX ingress for it. In-cluster, only the `config-adapter` component is allowed to talk to
the NiFi REST API (enforced via `NetworkPolicy`).

To reach the NiFi UI from a developer machine, use `kubectl port-forward`, e.g.:

```bash
kubectl -n <nifi-namespace> port-forward svc/nifi-nifi 8443:8443
# then open https://localhost:8443/nifi
```

Authentication still goes through Keycloak (OIDC).

## Deploy

```bash
# navigate to `deployment/` and run:
helmfile apply -i --selector component=nifi
```

### Migration from a pre-bootstrap deployment

If NiFi was previously deployed with a different `initial_admin_identity` (the human
operator's email, or the old `service-account-nifi-bootstrap` principal), changing it
in the chart values has **no effect on the running NiFi**: NiFi only honours the
Initial Admin Identity on the very first start, when it creates `users.xml` and
`authorizations.xml`. Existing PVCs already contain those files.

> **`just destroy-component` / `helm uninstall` is NOT enough.** Those only remove
> the Helm release; they do **not** delete the StatefulSet's PVCs (Kubernetes retains
> `volumeClaimTemplates` PVCs by design). The `config-nifi-nifi-0` PVC keeps the old
> `users.xml` / `authorizations.xml`, so a reinstall reuses the stale Initial Admin
> Identity and the bootstrap Job keeps getting `HTTP 403` ("Unable to view the user
> interface"). You must explicitly delete the auth files (or the `config` PVC) as shown
> below. Note this is purely a NiFi-side state reset — the Keycloak users and the
> `initialUserEmail` value are unaffected.


To migrate, wipe the auth files (or the whole `config` PVC) so NiFi rebuilds them
with the new initial admin and the bootstrap Job can finish the job. NiFi stores
these files on the `config` PVC under `persistent_conf/` (NOT `conf/`):

```bash
NS=<nifi-namespace>

# Stop NiFi and clear only the auth files (preserves flow / state / content).
kubectl -n $NS scale statefulset nifi-nifi --replicas=0
kubectl -n $NS wait --for=delete pod/nifi-nifi-0 --timeout=120s

# Run a tiny one-shot pod that mounts the config PVC and removes the auth files.
# The config PVC is mounted at /opt/nifi/nifi-current/persistent_conf in NiFi, so
# users.xml / authorizations.xml live at the PVC root here.
kubectl -n $NS run nifi-reset --rm -i --restart=Never --image=busybox \
  --overrides='{
    "spec": {
      "containers": [{
        "name": "reset",
        "image": "busybox",
        "command": ["sh","-c","rm -f /conf/users.xml /conf/authorizations.xml && ls -la /conf"],
        "volumeMounts": [{"name":"conf","mountPath":"/conf"}]
      }],
      "volumes": [{"name":"conf","persistentVolumeClaim":{"claimName":"config-nifi-nifi-0"}}]
    }
  }'

# Bring NiFi back up; the post-install Job (re-)runs on next helmfile apply.
helmfile apply -i --selector component=nifi
```

> Adjust the PVC name (`config-nifi-nifi-0`) to match your StatefulSet — verify with
> `kubectl -n $NS get pvc`. Note: `flow.json.gz` is NOT on this PVC and is left
> untouched, so existing flows are preserved.
